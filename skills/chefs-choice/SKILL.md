# Chef’s Choice

Choose an ambitious, well-matched approach while preserving every safety, authorization, and scope boundary.

## Contract

Use at least one genuinely useful skill, agent, connector, research capability, or heavyweight tool. Capability use must change the evidence, reasoning, implementation, or verification; ceremonial fan-out does not satisfy the contract.

Chef’s Choice governs resource selection and ambition. It does not define domain quality by itself. For substantive creative, technical, analytical, or design work, apply Exemplar when installed. If Exemplar is unavailable, use this compact fallback:

1. Identify the actual objective and evaluator.
2. Add one or two changes with the highest practical value.
3. Remove anything performing sophistication.
4. Verify the result against observable success evidence.

## Capability selection

Discover what is actually available before naming or promising a capability. Prefer one strong fit over a large council.

- **Open-ended direction:** use one deliberative or domain-specialist capability.
- **System understanding:** divide independent subsystems across parallel investigators.
- **Build work:** use architecture, design, accessibility, or testing help only where it changes the result.
- **Review and hardening:** use an adversarial or independent verifier with a concrete failure-mode brief.
- **Research:** use authoritative sources or diverse independent evidence, then synthesize and preserve disagreement.

Launch independent work in parallel when the host supports it. When a named capability is unavailable, choose an equivalent available capability or continue with the compact fallback; do not fail merely because one brand-name tool is missing.

## Scale test

Match spend to the task:

- A narrow task gets one well-chosen capability.
- A sprawling task may get a bounded fan-out with non-overlapping briefs.
- A mechanical task should not be inflated into a workflow.

State the selected capability and why it fits in one concise line.

## Guardrails

- Ambition never expands authorization.
- Confirm outward-facing or difficult-to-reverse actions unless the user already authorized them explicitly.
- Preserve repository and deployment safety rules.
- Read before editing and inspect source/installed state before creating or replacing resources.
- Do not expose secrets to delegated tools or external models.
- Keep dissent when independent reviewers identify different concrete failure modes.
- Run the relevant tests or acceptance checks before reporting completion.

## Output

Deliver the result, not a menu of unused possibilities. Report which capability materially helped, what landed, how it was verified, and any meaningful limitation that remains.
